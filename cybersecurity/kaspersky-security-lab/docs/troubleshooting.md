# Диагностика

## Наблюдение при повторной сборке

**Условие.** На Windows 11 проверена готовность к запуску 64-разрядных ВМ. Процессор предоставляет расширения виртуализации, а Windows сообщает `VirtualizationFirmwareEnabled=False` и `HypervisorPresent=False`. Это результат предварительной проверки хоста. [Запись измерений](../evidence/README.md)

**Исправление и результат.** После включения `SVM Mode` в UEFI и перезагрузки Windows сообщила `VirtualizationFirmwareEnabled=True`. VirtualBox запустил серверную ВМ в фоновом режиме. Точная позиция параметра зависит от версии UEFI. [Руководство Gigabyte B550M AORUS ELITE, стр. 25](https://download.gigabyte.com/FileList/Manual/mb_manual_b550m-aorus-elite_e_1201.pdf)

**Установка VirtualBox.** Первая попытка через EXE-обёртку завершилась кодом Windows Installer 1639 после передачи аргумента журналирования. Повторный вызов без этого аргумента вернул код 0. Наличие `VBoxManage.exe` на D: и вывод команды `VBoxManage --version` подтвердили установку.

**Автоматическая установка оценочных Windows.** Оба установщика показали сообщение о невозможности найти условия лицензии. В сгенерированном VirtualBox файле ответов загружались нужная редакция и подтверждение условий, но передавался пустой блок `UserData.ProductKey`. После удаления пустого блока и повторного запуска обе ВМ прошли этот этап и начали установку на виртуальный диск. [До исправления](../evidence/windows-setup-license-error.png) · [После исправления](../evidence/windows-setup-continued.png)

**Проверка EICAR.** При записи и отдельном чтении свежего образца событие KES отсутствовало. При проверке по требованию KES определил и удалил образец. Событие обнаружения найдено в KSC после синхронизации, отдельная сводка вирусной активности вернула 0 строк. Причина расхождения в этих прогонах пока не установлена. [Результаты](../evidence/README.md)

**Классификация USB.** VirtualBox передал два виртуальных диска по шине USB. Windows показала для обоих `DriveType=3` (`Fixed`). Для проверки запрета на съёмные диски подходят учебные флешки, которые видны в гостевой ОС как съёмные тома.

## Если KES-CLT теряет связь с KSC

Ниже порядок будущей диагностики. Для контролируемого прогона используется LINK-02 из [матрицы](verification.md).

1. **Сеть.** Проверить, что внутренние адаптеры ВМ подключены к одной сети VirtualBox, адреса и маска совпадают со схемой, а TCP 13000 доступен с KES-CLT. При недоступности порта проверить прослушивание порта на сервере и правило брандмауэра в пределах учебной подсети.
2. **Агент.** Проверить, что служба Агента запущена, и выполнить `klnagchk.exe` из каталога установки. Сверить адрес, порт и результат соединения. Успешный TCP-запрос подтверждает транспорт, а утилита помогает проверить соединение на уровне Агента.
3. **Идентификация.** Если TCP доступен, а Агент сообщает ошибку защищённого подключения, проверить адрес сервера в пакете, доверие к серверному сертификату и время систем. Если пакет указывает на неправильный сервер, собрать пакет с правильным адресом и сертификатом или воспользоваться штатной `klmover` по документации.
4. **Подтверждение.** После исправления выполнить `klnagchk` повторно, затем сверить последнее подключение, состояние клиента и применение политики в KSC.

[Порты KSC](https://support.kaspersky.com/ksc/15.1/158830) · [klnagchk](https://support.kaspersky.com/ksc/15.1/3912) · [Справка KSC по сертификатам и klmover](https://support.kaspersky.com/ksc/15.1)

Для каждого возникшего сбоя записывать симптом, условия, вывод диагностик до и после, установленную причину и фактическое действие. Если причина осталась предположением, пометить это в журнале.
